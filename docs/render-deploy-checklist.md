## Required Environment Variables

| Variable | Value | Purpose |
|---|---|---|
| `NODE_ENV` | `production` | Activates production mode |
| `DATABASE_URL` | `postgresql://...` | Auto-injected by Render PostgreSQL resource |
| `JWT_SECRET` | 32+ chars | Auto-generated by `render.yaml` (`generateValue: true`) |
| `ALLOW_AUTO_SEED` | `true` (démo) / `false` (prod) | Creates demo accounts on first deploy. **Set `false` for real production.** See `docs/demo-vs-production.md` |
| `SEED_TOKEN` | 32+ chars | Required to call `/api/seed` in production |
| `ENABLE_PUBLIC_RESTAURANT_REGISTRATION` | `false` | Blocks public restaurant registration (set `true` for demo onboarding) |
| `NEXT_PUBLIC_SHOW_DEMO_CREDS` | `false` | Hides demo credentials on login pages |

> ⚠️ See `docs/demo-vs-production.md` for the full distinction between demo and real production modes.

## Order of Operations in `render-start.sh`

The startup sequence is critical — getting the order wrong causes SaaS orphans:

```
1. Detect provider (postgres / sqlite) from DATABASE_URL
2. Copy the matching schema (postgres / sqlite) to prisma/schema.prisma
3. Verify provider with check-prisma-provider.cjs
4. Regenerate Prisma Client (rm -rf .prisma + npx prisma generate)
5. Diagnostics: check .next/, .next/BUILD_ID, node_modules/, @prisma/client
6. Apply migrations:
     postgres → npx prisma migrate deploy (fallback: db push --skip-generate)
     sqlite   → npx prisma db push --skip-generate
7. postgres only → run ensure-postgres-columns.cjs (safety net)
8. Run auto-seed.cjs (creates demo data if DB is empty)
9. Run backfill-accounts.cjs (attaches Account to restaurants/admins)
10. exec npx next start -p $PORT -H $HOSTNAME
```

**Why this order?** Auto-seed runs FIRST so that on a fresh DB, the demo Restaurant + Admins already exist. Backfill runs SECOND to attach an Account to those rows. If we ran backfill first, it would find nothing, and the seed-created restaurant/admins would stay orphan (no `accountId`) until the next restart.

## Deploy Procedure

### After any Prisma schema change

1. Push the code to `main`
2. Go to https://dashboard.render.com/web/srv-kfm-delice
3. Click **Manual Deploy** → **Clear build cache & deploy**
4. Wait 5–7 minutes
5. Check logs for the following sequence:
   ```
   [render-build] Provider: postgres
   [check-prisma-provider] ✓ Prisma provider OK
   [render-build] Build complete! Provider=postgres

   [render-start] Detected provider: postgres
   [render-start] Regenerating Prisma Client (provider=postgres)...
   [render-start] Checking Next.js build output...
   [render-start] Running prisma migrate deploy...
   [render-start] Running ensure-postgres-columns safety check...
   [render-start] Running auto-seed...
   [auto-seed] ✓ SaaS-coherent seed complete!
   [render-start] Running SaaS account backfill...
   [backfill-accounts] Done.
   [render-start] Starting Next.js server...
   ==> Deploy live
   ```

### After code-only changes (no Prisma schema change)

1. Push to `main`
2. Render auto-deploys (if webhook is working)
3. If not, do **Manual Deploy** → **Deploy latest commit**

## Common Issues

### 503 on `/menu` or any route

**Cause**: One of these — check Render logs to identify which:
1. `.next/` directory is missing → build failed silently
2. `node_modules/@prisma/client` is missing → `prisma generate` failed
3. Prisma Client has wrong provider (sqlite on a postgres DB)
4. App crashed during startup

**Diagnostic**: Look for the `[render-start] Checking Next.js build output...` block in logs. Any `WARNING:` line tells you what's missing.

**Fix**:
- If `WARNING: .next directory missing` → the build step failed. Check `[render-build]` logs above. Re-run with **Clear build cache & deploy**.
- If `WARNING: @prisma/client missing` → `prisma generate` failed. Check the line above for the error.
- If `provider = "sqlite"` error → see next section.

### "the URL must start with the protocol file:"

**Cause**: Prisma Client was generated with SQLite schema instead of PostgreSQL. The standalone bundle (when `output: "standalone"` was set) cached a stale SQLite client.

**Fix**: This was definitively fixed by removing `output: "standalone"` from `next.config.ts`. The server now uses `next start` which reads Prisma Client from `node_modules/.prisma/client/` directly. If you still see this error:
1. Confirm `next.config.ts` does NOT contain `output: "standalone"`
2. Confirm `render-start.sh` ends with `exec npx next start -p "$PORT" -H "$HOSTNAME"`
3. Do **Clear build cache & deploy** on Render

### "column does not exist in the current database"

**Cause**: A migration didn't run or the safety net missed a column.

**Fix**: Check logs for `[ensure-columns]` and `[render-start]` output. The safety net in `db.ts` + `ensure-postgres-columns.cjs` should auto-add missing columns. If not, add the column to the `REQUIRED_COLUMNS` array in `scripts/ensure-postgres-columns.cjs`.

### Login returns 500 without debug info

**Cause**: Production mode hides technical errors (by design).

**Fix**: Check Render logs (not the API response) for the actual error. The `console.error("[login] Error:", error)` in the route logs the full error.

### SaaS fields (`accountId`, `canCreateRestaurant`) are null after deploy

**Cause**: Either auto-seed didn't run, or backfill-accounts didn't run, or they ran in the wrong order.

**Fix**:
1. Check logs for `[auto-seed] ✓ SaaS-coherent seed complete!` — if missing, the seed failed. Look for `[auto-seed] Error:` above.
2. Check logs for `[backfill-accounts] Summary:` — should show `Accounts created: 1` or `Restaurants linked: 1` on first deploy.
3. If both ran but fields are still null, the Prisma Client may be stale. Do **Clear build cache & deploy**.
4. As a last resort, run backfill manually:
   ```bash
   # In Render shell, or locally with the production DATABASE_URL
   node scripts/backfill-accounts.cjs
   ```

## Verifying Account linking after seed

After a successful deploy, the database should contain:

```
Account (1)
  ├─ name: "KFM Delice"
  ├─ plan: "pro"
  ├─ maxRestaurants: 5
  ├─ maxSecondaryRestaurants: 4
  └─ restaurants: [Restaurant]
       ├─ name: "KFM Delice"
       ├─ accountId: <account.id>  ← NOT null
       ├─ type: "principal"        ← NOT null/empty
       └─ admins: [Admin]
            ├─ admin@kfm-delice.com
            │   ├─ accountId: <account.id>
            │   ├─ canCreateRestaurant: true
            │   └─ restaurantCreationLimit: 4
            ├─ manager@kfm-delice.com
            │   ├─ accountId: <account.id>
            │   ├─ canCreateRestaurant: false
            │   └─ restaurantCreationLimit: 0
            └─ staff@kfm-delice.com
                ├─ accountId: <account.id>
                ├─ canCreateRestaurant: false
                └─ restaurantCreationLimit: 0
```

You can verify with the `/api/account/me` endpoint (requires login token). See step 5 in Post-Deploy Verification above.

## E2E Tests

After a successful deploy, run the E2E test suites to verify everything works end-to-end.

### E2E Live (general API tests)

```bash
BASE_URL=https://kfm-delice-ggb4.onrender.com \
E2E_SLUG=kfm-delice \
E2E_PLATFORM_EMAIL=admin@restaurantpro.com \
E2E_PLATFORM_PASSWORD=platform2024 \
E2E_ADMIN_EMAIL=admin@kfm-delice.com \
E2E_ADMIN_PASSWORD=kfm2024 \
E2E_MANAGER_EMAIL=manager@kfm-delice.com \
E2E_MANAGER_PASSWORD=manager2024 \
E2E_CUSTOMER_EMAIL=aminata@gmail.com \
E2E_CUSTOMER_PASSWORD=client123 \
E2E_DRIVER_EMAIL=moussa@kfm-delice.com \
E2E_DRIVER_PASSWORD=driver123 \
E2E_SAFE_MODE=true \
python3 scripts/e2e-live.py
```

Set `E2E_SAFE_MODE=true` when running against production to skip destructive tests (create/delete).

### E2E SaaS (Account / quotas / secondary restaurants)

```bash
BASE_URL=https://kfm-delice-ggb4.onrender.com \
E2E_PLATFORM_EMAIL=admin@restaurantpro.com \
E2E_PLATFORM_PASSWORD=platform2024 \
E2E_TEST_PREFIX="E2E KFM $(date +%s)" \
E2E_SAFE_MODE=true \
python3 scripts/e2e-saas.py
```

This script tests:
1. Platform admin login
2. Account creation
3. Main restaurant creation
4. Admin SaaS fields verification (accountId, canCreateRestaurant, limit)
5. Quota endpoint
6. Secondary restaurant creation
7. Quota decrease verification
8. Denial of second main restaurant
9. Over-quota blocking

## 503 Troubleshooting

If you see HTTP 503, see `docs/render-503-troubleshooting.md` for a comprehensive guide covering:
- Wrong host (not 0.0.0.0)
- Wrong port
- Prisma Client wrong provider
- Prisma 7 downloaded by npx
- Missing .next/BUILD_ID
- Missing DATABASE_URL
- Blocking migration
- Seed crash
- Service hibernation (free tier)
