# Task 3.1 — WebSocket Real-Time Communication

## Summary
Added WebSocket real-time communication to RestoProGN using the `ws` package, with HTTP polling as fallback when WebSocket is disconnected. The WebSocket server runs as a singleton within the Next.js process on port 3001, and clients connect through the Caddy gateway using the XTransformPort mechanism.

## Files Created

### 1. `/src/lib/websocket-server.ts`
- Singleton WebSocket server manager using the `ws` package
- Starts WSS on port 3001 on first call to `getWebSocketServer()`
- Client tracking with `userId:userType` key format
- Functions: `getWebSocketServer()`, `broadcastToType()`, `sendToUser()`, `broadcastAll()`, `getConnectedCount()`, `getConnectedByType()`
- Handles duplicate connections (old socket closed when same client reconnects)
- Error handling for EADDRINUSE (port already in use)

### 2. `/src/lib/ws-events.ts`
- Event type constants for all WebSocket events
- Events: ORDER_NEW, ORDER_STATUS_CHANGED, ORDER_ASSIGNED, DRIVER_LOCATION_UPDATE, DRIVER_STATUS_CHANGED, RESERVATION_NEW, RESERVATION_STATUS_CHANGED, ADMIN_NOTIFICATION, TRACKING_UPDATE, WS_CONNECTED

### 3. `/src/hooks/use-websocket.ts`
- Client-side React hook for WebSocket communication
- Connects through Caddy gateway via `XTransformPort=3001`
- Auto-reconnect on disconnect (configurable delay)
- Event listener registration (`on`/`off` methods)
- Proper cleanup on unmount
- Configurable options: `enabled`, `autoReconnect`, `reconnectDelay`

### 4. `/src/app/api/ws-notify/route.ts`
- HTTP endpoint for triggering WebSocket broadcasts
- POST: accepts `{ event, data, targetType, targetUserId }` — broadcasts to user type or specific user
- GET: returns WS server status and connected client count
- Requires authentication (protected by middleware)

## Design Decisions

1. **WS Server in Next.js Process**: The WSS runs as a singleton inside the Next.js server process on port 3001. This allows API routes to directly import and call broadcast functions without HTTP overhead.

2. **Dynamic Import Pattern**: All WS broadcasts use `await import('@/lib/websocket-server')` inside try/catch blocks. This ensures:
   - Lazy initialization (WSS starts only when first needed)
   - API routes don't break if WS server fails to start
   - HTTP polling remains as automatic fallback

3. **Caddy Gateway Routing**: Clients connect via `ws://host/?XTransformPort=3001&userId=X&userType=Y`. The Caddy gateway proxies this to `localhost:3001`.

4. **Coexistence Approach**: Existing polling intervals are preserved. WebSocket is additive — when connected, real-time updates are delivered instantly. When disconnected, polling continues as before.
